클라이언트 앱에서 수집한 이벤트 로그와 서버 DB에 쌓인 트랜잭션 데이터는 원칙적으로 같은 사실을 가리켜야 한다. 사용자가 앱에서 결제 버튼을 눌렀다면 로그에도 결제 이벤트가 남고, DB에도 결제 레코드가 남는 게 맞다. 그런데 실무에서 두 숫자를 나란히 놓고 비교해보면 거의 항상 차이가 난다. 로그 기준 결제 시도 건수와 DB 기준 결제 완료 건수가 몇 퍼센트씩 어긋나는 건 이상 현상이 아니라 데이터 파이프라인을 다뤄본 사람이라면 누구나 마주치는 기본값에 가깝다. 이 글에서는 그 차이가 구조적으로 왜 발생할 수밖에 없는지를 원인별로 정리하고, 그렇다면 분석 목적에 따라 클라이언트 로그와 DB 중 어느 쪽을 신뢰할 기준으로 삼아야 하는지를 정리한다.

## 원칙적으로 같아야 하는데, 왜 항상 다른가

두 데이터가 어긋나는 원인은 대부분 "같은 사건을 서로 다른 설계 철학을 가진 두 시스템이 각자의 방식으로 기록한다"는 사실로 수렴한다. 하나씩 뜯어보면 다음과 같다.

### 1. 로그는 "의도"를, DB는 "결과"를 기록한다

클라이언트 로그는 사용자가 화면에서 어떤 행동을 취했는지, 즉 액션이 발생한 시점을 기록한다. 반면 DB 레코드는 그 액션이 서버 쪽 비즈니스 로직을 통과해서 최종적으로 확정된 결과를 기록한다. 예를 들어 외화 충전 서비스에서 사용자가 충전 버튼을 누르면 클라이언트는 그 즉시 "충전_시도" 이벤트를 로그로 남긴다. 하지만 이 요청이 서버에 도달해 잔액 확인, 환율 적용, PG사 승인까지 모두 통과해야 DB에 "충전_완료" 레코드가 생긴다. 그 사이에 잔액 부족, PG 타임아웃, 서버 측 유효성 검증 실패 같은 이유로 요청이 중간에 걸러지면, 로그에는 시도 이벤트가 남아 있는데 DB에는 대응하는 레코드가 없는 상태가 된다. 두 시스템이 애초에 서로 다른 단계를 기록하고 있으므로, 이 경우의 불일치는 결함이 아니라 설계상 당연한 결과다.

### 2. 상태 이력과 속성값을 정교하게 남겨도 좁혀지지 않는 이유

여기서 자연스럽게 반론이 나올 수 있다. DB도 최종 상태 하나만 남기지 말고 상태 전이 전체를 기록하는 히스토리(history) 테이블을 만들면 되지 않나. 로그도 이벤트 이름만 남기지 말고 금액·단계·에러코드 같은 property를 촘촘히 붙이면 정보량 차이가 사라지지 않나. 실제로 이 방향의 개선은 실무에서 흔히 이루어지고 어느 정도는 유효하다. 문제는 양쪽을 아무리 정교하게 만들어도 두 데이터가 완전히 합치되지는 않는다는 데 있다. 그 이유는 "기록하는 대상이 다르다"는 층위보다 한 단계 더 아래, 즉 "그 기록이라는 행위 자체가 서로 독립된 두 개의 쓰기 경로 위에서 일어난다"는 구조적 문제에 있다.

**이중 쓰기 문제(dual-write problem).** 하나의 논리적 사건(사용자의 충전 시도)을 기록하기 위해 실제로는 로그 시스템에 쓰는 것과 DB에 쓰는 것, 물리적으로 분리된 두 개의 쓰기 작업이 일어난다. 이 두 쓰기를 하나의 트랜잭션으로 묶어주는 장치는 없다. DB 쓰기는 성공하고 로그 쓰기는 실패할 수도, 그 반대도 가능하다. 각각의 쓰기가 개별적으로는 아무리 견고해도(로그는 재시도·큐잉으로, DB는 ACID 트랜잭션으로) 그 둘을 묶는 상위 트랜잭션이 없다는 사실은 바뀌지 않는다. 이는 분산 시스템에서 "DB에 쓰고 메시지 큐에도 발행해야 하는" 상황에서 흔히 마주치는 이중 쓰기 문제와 본질적으로 같은 구조다. 서버 쪽에서는 transactional outbox 패턴처럼 DB 커밋과 이벤트 발행을 같은 트랜잭션 경계 안에 묶어 이 문제를 어느 정도 완화할 수 있지만, 클라이언트 로그는 애초에 서버 트랜잭션 경계 바깥, 즉 사용자 기기 위에서 발생하기 때문에 이런 완화조차 적용할 수 없다. DB 히스토리 테이블을 아무리 촘촘하게 설계해도, 그것과 짝을 이루는 클라이언트 로그 이벤트가 같은 트랜잭션 안에서 함께 확정되지 않는다는 사실은 그대로 남는다.

**DB의 "결과"도 절대적 진실은 아니다.** DB를 기준점으로 삼는 논리는 DB가 서버가 확인한 사실만을 기록한다는 전제 위에 있다. 하지만 서버 자신도 외부 시스템(PG사 등)과의 통신 결과를 항상 확실하게 알 수 있는 건 아니다. PG사에 승인 요청을 보냈는데 응답이 타임아웃되면, 서버는 그 요청이 실제로 처리됐는지 알 수 없는 모호한 상태에 놓인다. 이때 서버가 보수적으로 "실패"로 기록했는데 실제로는 PG사에서 승인이 됐다면, 이후 PG사의 비동기 웹훅이나 정산 배치를 통해 뒤늦게 상태가 "완료"로 정정되는 일이 생긴다. 즉 DB 히스토리 테이블도 특정 시점에는 서버가 그 순간까지 확인한 최선의 추정치를 담고 있을 뿐이고, 나중에 재조정(reconciliation)되며 값이 바뀔 수 있는 잠정적인 기록이다. 이 정정 과정과 클라이언트 로그가 동기화될 방법은 원천적으로 없다. 로그는 사용자가 버튼을 누른 순간의 스냅샷이고, DB 히스토리는 서버가 사후에도 계속 갱신하는 살아있는 기록이기 때문이다.

**로그에는 없는데 DB에는 있는 상태 전이.** DB 히스토리에는 클라이언트 이벤트와 전혀 무관하게 생기는 상태 전이가 있다. PG사의 지연 웹훅에 의한 뒤늦은 승인 처리, CS 상담원의 수동 환불·취소 처리, 심야 배치 잡이 타임아웃 건을 일괄로 실패 처리하는 경우가 대표적이다. 이런 상태 변화는 애초에 클라이언트가 관여하지 않은 채로 서버 내부에서만 일어나기 때문에, 클라이언트 로그의 property를 아무리 풍부하게 설계해도 대응하는 이벤트가 존재할 수 없다.

**DB에는 없는데 로그에는 있는 사건.** 반대 방향의 비대칭도 있다. 클라이언트 쪽 입력값 검증에서 걸려 서버로 요청 자체를 보내지 않은 경우, UI 렌더링 지연 때문에 사용자가 버튼을 여러 번 눌러 로그 이벤트가 중복 생성된 경우, 클라이언트 SDK가 네트워크 상태를 감지하고 자체적으로 재시도를 시도하다 끝내 한 번도 서버에 도달하지 못한 경우처럼, 서버가 요청 자체를 받아본 적이 없는 사건들이다. 서버 쪽 히스토리 테이블을 아무리 정교하게 설계해도 이런 사건은 잡아낼 방법이 없다. 서버가 그 요청의 존재 자체를 모르기 때문이다.

![클라이언트 로그가 관측한 상태 전이와 DB 히스토리가 기록한 상태 전이가 서로 다른 집합임을 보여주는 벤 다이어그램, 로그에만 있는 사건과 DB에만 있는 사건이 각각 표시됨](/assets/images/posts/client-log-vs-db-observation-asymmetry.svg)

**두 기록의 "시각"조차 근사치다.** 두 데이터를 이어 붙일 때 흔히 쓰는 방법이 타임스탬프 기준 조인이다. 그런데 클라이언트 기기의 시계와 서버의 시계는 완벽하게 동기화되어 있지 않다. NTP 동기화 지연, 사용자가 기기 시간을 수동으로 바꾼 경우, 타임존 처리 로직의 미묘한 버그 등으로 클라이언트 타임스탬프와 서버 타임스탬프 사이에는 항상 어느 정도의 오차가 있다. 트랜잭션이 초당 수십~수백 건씩 발생하는 서비스에서는 이 오차가 "같은 시점"으로 조인해야 할 로그와 DB 레코드를 서로 다른 시점의 레코드로 잘못 매칭시키는 원인이 된다. 이건 유실이나 중복과는 또 다른 층위의 오차이고, 로그와 DB 양쪽 모두 아무리 정교해져도 시계 자체가 물리적으로 완벽히 일치할 수 없는 한 사라지지 않는다.

이 다섯 가지가 말하는 건 히스토리 테이블이나 풍부한 property 설계가 무의미하다는 게 아니라, 그것들이 좁히는 격차와 좁히지 못하는 격차가 서로 다르다는 것이다. 정교화는 각 시스템이 "자신이 관측한 것"을 더 상세하게, 더 누락 없이 기록하도록 도와준다. 하지만 두 시스템이 서로 다른 관측 지점, 서로 다른 쓰기 경로, 서로 다른 시계 위에 있다는 구조적 조건 자체는 정교화로 해소되지 않는다. 실무에서 이 격차에 대응하는 현실적인 방법은 완전한 일치를 포기하고, 클라이언트가 요청을 보낼 때 고유한 요청 ID(idempotency key)를 생성해 로그 이벤트와 서버 요청 양쪽에 함께 실어 보내는 것이다. 이렇게 하면 나중에 두 데이터를 조인할 때 타임스탬프의 근사치가 아니라 정확한 키로 같은 논리적 사건을 짝지을 수 있고, 중복 전송된 로그도 이 ID를 기준으로 걸러낼 수 있다. 다만 이 방식도 클라이언트가 요청을 아예 만들지 못하고 죽는 경우(로그에도 DB에도 남지 않는 사건)나 서버 내부에서 클라이언트 관여 없이 발생하는 상태 전이(DB에만 있는 사건)까지 해결해주지는 못한다. 이중 쓰기 문제와 관측 비대칭이라는 구조적 한계 안에서 조인 정확도를 높이는 수준의 개선이지, 격차 자체를 없애는 해법은 아니라는 뜻이다.

### 3. 전송 보장 방식이 다르다: at-least-once vs 트랜잭션

DB 트랜잭션은 ACID(원자성·일관성·고립성·지속성)를 보장하도록 설계된다. 커밋이 되면 반드시 남고, 실패하면 롤백되어 아예 없던 일이 된다. 반면 클라이언트 로깅 SDK는 대부분 "at-least-once delivery"를 목표로 동작한다. 네트워크가 불안정한 모바일 환경에서 이벤트 유실을 최소화하기 위해, 전송 실패 시 재시도를 하고 확인 응답을 받을 때까지 로컬에 큐잉(queuing)해둔다. 여기서 큐잉이란 이벤트를 발생 즉시 서버로 보내는 대신, 기기 안의 임시 저장소(큐)에 우선 쌓아두고 전송이 성공했다는 확인 응답(ACK)을 받을 때까지 그 저장소에 계속 남겨두는 방식을 말한다. 전송에 실패하면 큐에서 빼지 않고 일정 시간 뒤 다시 시도하며, 이 재시도는 앱이 백그라운드로 전환되거나 잠시 꺼졌다 켜져도 큐 자체가 남아 있는 한 이어진다. 서버 입장에서 요청을 정상적으로 받아 처리했더라도 그 처리 결과(ACK)가 클라이언트로 돌아오는 길에 유실되면, 클라이언트는 실패로 판단하고 같은 이벤트를 다시 보낸다. 이 구조에서는 두 가지 종류의 오차가 동시에 생긴다. 하나는 이렇게 재시도 과정에서 같은 이벤트가 중복 전송되어 로그 쪽 건수가 부풀려지는 경우고, 다른 하나는 앱이 강제 종료되거나 사용자가 네트워크가 끊긴 상태에서 앱을 완전히 삭제·재설치해버려서 큐에 쌓인 이벤트가 끝내 전송되지 못하고 유실되는 경우다. DB는 이런 종류의 중복이나 유실이 구조적으로 발생하지 않도록 설계된 시스템이고, 로그는 애초에 그런 트레이드오프를 감수하고 만들어진 시스템이라는 차이가 여기서 드러난다.

### 4. 네트워크와 디바이스 환경은 통제 밖의 변수다

클라이언트는 서버와 달리 사용자의 디바이스, 네트워크 상태, OS 정책이라는 통제 불가능한 변수 위에서 동작한다. 지하철처럼 네트워크가 불안정한 환경에서는 이벤트 전송이 지연되거나 실패할 확률이 높아진다. iOS와 Android 모두 배터리 최적화 정책상 백그라운드 네트워크 요청을 제한하는데, 이 때문에 앱이 백그라운드로 전환된 직후 큐에 쌓인 로그가 즉시 전송되지 못하고 다음 포그라운드 진입까지 지연되는 경우도 흔하다. 그 사이에 사용자가 앱을 삭제하거나 오래 재실행하지 않으면 그 이벤트는 영영 서버에 도달하지 못한다. 또한 트래킹 차단 기능이 켜진 기기, 특정 방화벽 정책이 적용된 기업 네트워크, 광고 차단 확장 프로그램이 깔린 환경에서는 로깅 SDK의 요청 자체가 차단되기도 한다. DB 쪽 트랜잭션은 서버 인프라 내부에서만 발생하므로 이런 외부 변수에 노출되지 않는다.

### 5. 앱 버전 파편화와 로깅 스키마의 역사

서비스가 일정 기간 이상 운영되면 사용자들은 서로 다른 버전의 앱을 쓰게 된다. 새 버전에서 이벤트 이름이나 파라미터 구조를 바꿨더라도, 구버전을 아직 쓰고 있는 사용자의 단말에서는 예전 스키마로 로그가 올라온다. 강제 업데이트 정책이 없는 서비스라면 이런 구버전 트래픽이 몇 달, 길게는 몇 년까지도 섞여 들어온다. 반면 DB 스키마와 서버 로직은 서버 배포 시점에 일괄적으로 바뀌기 때문에, 이 시차 동안 클라이언트 로그와 DB가 서로 다른 정의를 기준으로 같은 사건을 기록하는 구간이 생긴다. 이 문제는 순수하게 기술적인 유실·중복과는 성격이 달라서, 집계 로직에서 버전별 스키마를 명시적으로 분기해서 처리하지 않으면 겉보기에는 데이터 불일치처럼 보이는 결과가 계속 나온다.

### 6. ETL 파이프라인을 통과하며 추가로 벌어지는 차이

로그든 DB든 원본 그대로 분석에 쓰이는 경우는 드물고, 대개 ETL 과정을 거쳐 별도의 분석 테이블로 적재된다. 이 과정에서 늦게 도착한 이벤트(late-arriving data)를 특정 마감 시점 이후로는 집계에 포함하지 않는 정책, 중복 제거(dedup) 로직의 판단 기준, 봇 트래픽이나 QA 계정 필터링 기준이 각각 다르게 설계되어 있으면 최종적으로 리포트에 찍히는 숫자는 원본 로그·원본 DB보다 한 단계 더 벌어진다. 여기에 배치 스케줄이 다른 두 파이프라인(로그 집계 배치와 DB 정산 배치)의 실행 시각이 다르면, 같은 날짜 기준으로 조회했을 때도 어느 시점의 스냅샷을 보느냐에 따라 숫자가 미묘하게 달라진다.

## 그래서 "몇 %까지는 정상"인가

이런 구조적 이유들 때문에 클라이언트 로그와 DB 데이터가 100% 일치하는 것은 애초에 달성 가능한 목표가 아니다. 실무에서 접근하는 방식은 "완전히 일치시킨다"가 아니라 "차이의 크기와 원인을 설명 가능한 상태로 관리한다"는 쪽에 가깝다. 구체적으로는 다음과 같은 절차를 거친다.

우선 두 소스 간 불일치율을 상시 모니터링하는 지표를 만든다. 예를 들어 일별로 (로그 기준 이벤트 건수 - DB 기준 레코드 건수) / DB 기준 레코드 건수를 계산해서 대시보드로 추적한다. 이 값이 특정 임계치(서비스 특성에 따라 다르지만 보통 한 자릿수 퍼센트 초반) 안에서 안정적으로 유지된다면, 그 차이는 위에서 설명한 구조적 원인들로 설명 가능한 정상 범위로 간주한다. 반대로 이 값이 평소보다 갑자기 튀거나 추세적으로 벌어지기 시작하면, 그때는 로깅 SDK 배포 이슈, 특정 앱 버전의 이벤트 누락, 서버 장애처럼 조사가 필요한 이상 신호로 다룬다. 즉 불일치율 자체를 없애는 게 목표가 아니라, 불일치율의 기준선(baseline)을 정해두고 그 기준선에서 벗어나는 변화를 감지하는 것이 목표가 된다.

## 클라이언트 로그를 봐야 하는 경우, DB를 봐야 하는 경우

두 소스가 완전히 같아질 수 없다는 걸 받아들이고 나면, 다음 질문은 "그럼 어떤 분석을 할 때 어느 쪽을 기준으로 삼아야 하는가"다. 이 판단은 분석 목적이 "사용자의 행동과 의도"를 보는 것인지, 아니면 "확정된 비즈니스 결과"를 보는 것인지에 따라 갈린다.

### 클라이언트 로그가 우선인 경우

퍼널 분석, 화면 진입·이탈률, 버튼 클릭률, A/B 테스트의 노출·전환 측정처럼 사용자가 실제로 무엇을 시도했는지가 중요한 분석에는 클라이언트 로그를 기준으로 삼는다. 이런 지표들은 애초에 서버 트랜잭션으로 완결되지 않는 행동(화면을 봤다, 버튼을 눌렀다가 취소했다, 특정 단계에서 이탈했다)을 다루기 때문에 DB에는 대응하는 레코드 자체가 없는 경우가 많다. 예를 들어 외화 충전 신청 화면에서 사용자가 어느 단계(금액 입력, 결제수단 선택, 최종 확인)에서 가장 많이 이탈하는지를 분석하려면, 완결된 충전 건만 남아 있는 DB로는 이탈 지점을 재구성할 수 없고 각 단계 진입 이벤트가 남아 있는 클라이언트 로그가 유일한 소스가 된다.

### DB가 우선인 경우 (Source of Truth)

반대로 매출, 정산, 사용자 잔액, 결제 성공 건수처럼 금전적으로 확정된 사실을 다루는 지표는 항상 DB를 기준으로 삼아야 한다. 회계·정산·규제 보고에 쓰이는 숫자가 로그 기준으로 집계되어 있다면, 그 숫자는 애초에 성립하지 않은 시도 건까지 포함하거나 중복 전송된 이벤트를 이중 계상할 위험을 안고 있다. DB는 트랜잭션 무결성이 보장된 시스템이므로, "실제로 얼마가 오갔는가"라는 질문에는 DB가 유일하게 신뢰할 수 있는 답을 준다. 이 원칙은 분석 리포트뿐 아니라 사내 대시보드, 외부 공시 자료 어디에도 예외 없이 적용해야 한다.

### 두 소스를 함께 봐야 하는 경우

두 소스가 서로를 검증하는 역할을 하는 경우도 있다. 대표적으로 결제 이탈의 원인을 분석할 때는, DB 기준으로 "결제 시도 대비 완료 비율"이 특정 구간에서 낮다는 걸 먼저 확인한 다음, 같은 구간에 대응하는 클라이언트 로그를 열어 사용자가 실제로 어떤 에러 화면을 봤는지, 어느 단계에서 뒤로가기를 눌렀는지를 재구성하는 식이다. DB만 보면 "왜" 떨어졌는지 알 수 없고, 로그만 보면 "실제로 얼마나" 영향이 있었는지 확정할 수 없기 때문에, 이런 원인 분석성 작업은 두 소스를 교차 검증하는 방식으로 진행해야 한다.

## 결론

클라이언트 로그와 DB는 같은 사건을 서로 다른 신뢰 모델 위에서 기록하는 두 개의 독립된 시스템이다. 로그는 유실을 감수하더라도 사용자의 모든 행동 의도를 최대한 넓게 포착하는 쪽으로 설계되어 있고, DB는 확정된 결과만을 무결성 있게 남기는 쪽으로 설계되어 있다. 이 둘을 같은 잣대로 놓고 "왜 숫자가 안 맞느냐"고 묻는 것 자체가 질문의 전제가 잘못된 경우가 많다. 실무에서 데이터를 다루는 입장에서 해야 할 일은 두 시스템의 불일치를 없애는 것이 아니라, 불일치가 설명 가능한 범위 안에 있는지를 관리하고, 지금 하려는 분석이 "사용자의 의도"를 봐야 하는 질문인지 "확정된 결과"를 봐야 하는 질문인지를 먼저 구분한 다음 그에 맞는 소스를 고르는 것이다.
